## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Why.** The plugin's tests run against minimal CLAP and VST3 hosts the project wrote itself. Real hosts differ in:
- state restore;
- note frames and note-offs at a loop seam;
- transport positions, loops and pre-roll;
- latency compensation;
- resampling;
- multi-output routing (task-256).

Several bugs showed up only in REAPER: task-226's timeline-start bugs, task-242's note-mode PCF and task-258's 303 left sliding after a send change. The user agreed (2026-11-18) to an integration test that renders REAPER projects through REAPER's command line. On 2026-11-21 the user set the order: after task-256 (the per-device outputs) and before task-258, which adds its own case to this harness. The task was reassigned to @agent-complex for its scope.

**Shape.**
- **Off by default, like ORB_CD_ISO.** The test runs only when `ORB_REAPER` is set to the REAPER executable (on macOS `/Applications/REAPER.app/Contents/MacOS/REAPER`). Otherwise it skips with a message. CI does not run it, because REAPER is licensed software.
- **Plugins from the fresh build only, with no install (user's decision, 2026-11-21).**
  - Build the bundles (`cargo xtask bundle orb-plugin --release`, into `target/bundled`).
  - Give REAPER a scratch config of its own: `REAPER -cfgfile <scratch>/reaper.ini ...`. Its VST and CLAP plugin paths list only the folder holding the fresh bundles. They replace REAPER's default list, so `/Library/Audio/Plug-Ins` and `~/Library/Audio/Plug-Ins` (where the user's root-owned installed copies live) are never scanned.
  - Nothing is copied into a plugin folder, and the user's own REAPER config and plugin caches are never read or written.
  - Confirm against the pinned REAPER version:
    - the exact `reaper.ini` keys for the VST and CLAP paths;
    - whether `-cfgfile` also moves the resource folder and the plugin caches (`reaper-vstplugins*.ini`, `reaper-clap*.ini`). If it does not, also give the test its own empty resource folder so REAPER scans fresh.
  - The test checks that REAPER loaded the fresh build, not some other copy: for example, the bundle path in the scratch plugin cache, or a build id the plugin writes into its state or log. It fails otherwise.
- **Fixtures.** Committed `.RPP` projects, each holding the plugin state in its plugin block: the base64 VST3 or CLAP state, whose JSON fields include the song, the patterns and the mode. Generate them from a template with a small tool, so a fixture can be rebuilt when the state format changes.
- **Rendering.** Run `REAPER -cfgfile ... -nosplash -renderproject X.RPP` into a scratch folder, check the exit status, and read the WAVs. Render stems where a case needs the device tracks.
- **Comparison.** Compare against orb-player's render of the same song in pattern mode, offset by the known latency (docs/plugin.md section 4). The tolerance is documented per case: drum notes against pattern steps differ by up to 1 LSB (task-243), plus the task-227 timing gap.
- **Cases:**
  - 303 notes with a slide (note mode);
  - an 808 and a 909 pattern dragged out (task-203), played in note mode against the same pattern, with the PCF inserted (task-242);
  - Latch Pattern Mode over a looped time selection;
  - a 48 kHz project (resampling);
  - multi-output (task-256): the four device outputs routed to their own tracks. The Mix renders bit-identical to the same project with no outputs routed, and each device track carries only its device. The device tracks match orb's per-channel render of the same song within the documented tolerance.
- **Version.** Pin and document the REAPER version used. The RPP format and the CLI behave differently between versions.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Opt-in REAPER render tests for the plugin, on branch worktree-agent-a3afcb92c19d93a76 (one commit).

What: crates/orb-plugin/tests/reaper.rs runs only with ORB_REAPER set (skips with a message otherwise; macOS only). It builds the bundles (cargo xtask bundle orb-plugin --release) and renders 20 committed fixtures (10 cases, each as VST3 and CLAP) with REAPER 7.86 -newinst -nosplash -ignoreerrors -cfgfile <scratch>/reaper.ini -renderproject. -cfgfile moves REAPER's whole resource folder, the plugin caches included, to target/reaper/<case>.<format>/resources. The scratch ini lists only target/bundled in vstpath_arm64 and clap_path_macos-aarch64. vstfullstate=33605 stops REAPER from adding the VST3 default folders, and the test fails if the ini no longer lists only target/bundled after a render. coreaudiobs plus <none> devices select the dummy audio device; these keys were found in REAPER's arm64 code. A new plugin activation log (ORB_PLUGIN_LOAD_LOG, src/load_log.rs, dladdr) must name only the fresh bundle's library at the project's rate, or the test fails. Nothing is installed, and the user's REAPER, its config and its caches were never touched.

Fixtures: examples/reaper_fixtures.rs makes them from tests/reaper/template.RPP and tests/reaper/cases.rs, using REAPER 7.86's VST3 and CLAP chunk formats with the plugin's nice-plug JSON state. MIDI items count in frames. the_fixtures_are_current (always runs) fails on a stale fixture.

Results: every master render, in both formats, is bit for bit the plugin's process side driven in-process as REAPER drives it (latency compensated: frame j = plugin frame j+64, j+105 at 48 kHz). The four cases met:
- 303 slide and 808/909 drag-out with the PCF, in note mode, against orb-player's pattern-mode render: with the notes aligned to the pattern's blocks, within 1 LSB. The 303's first note-off is moved to tick 25 in that fixture; the clip's tick 24 differs by up to 0.0045 (task-265). At the clip's own times the bounds are measured ceilings of task-227's gap (303 0.1497, 808 1.5874, 909 1.7431).
- 48 kHz: bit for bit the in-process plugin (Core).
- Multi-output: the Mix is bit for bit the same routed or not. Each device track is its Core bus bit for bit, except the VST3 host's 0 below about 1e-16 (allowed on the VST3 stems only) and the CLAP host's +0 for -0 (values on the CLAP stems only).

Not met: Latch over a loop. REAPER's CLI render does not loop; the loop_ignored pin, compared bit for bit, fails once it does. Follow-up task-264.

Findings:
- Plugin bug task-263: when a block starts exactly on a step tick (125 BPM, bar 2), the extrapolated host position is 768.0 or 767.9999999999999 by the call start, so the output depends on the host's buffer size (48 kHz Latch up to 0.16, 44.1 kHz note-mode PCF up to 0.12). The test uses 120 BPM to stay clear of it.
- Clip/pattern first-gate discrepancy task-265.

Docs: docs/plugin.md 7.1 (and sections 1, 4, 7), docs/building.md variables, AGENTS.md (the test variables, ORB_PLUGIN_LOAD_LOG, CARGO_TARGET_DIR).
Tests: cargo test 973 passed, 0 failed (before review); after review round 2: cargo test -p orb-plugin 137 passed, REAPER run 2 passed (60 s), clippy and nightly fmt clean.
