## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The user's report (2026-11-17), Ableton Live 12 Lite on macOS, VST3: when the plugin window is resized up or down, the panel's scale jumps around instead of following the window smoothly. Recording: ~/Documents/ableton_resize_weirdness.mp4 on the user's machine (extract frames with ffmpeg into a scratch folder to see it). REAPER does not show it (task-224 fixed REAPER's resize recursion: crates/orb-plugin/src/editor.rs HostProxy, docs/plugin.md section 10).

Not a release blocker (the user): task-215 and task-230 do not depend on it.

Investigate how Live drives the VST3 view's size (checkSizeConstraint, onSize, canResize, the editor's request_resize and the aspect/scale logic in editor.rs and baseview 0.4.2) and why the scale oscillates: e.g. a round trip between the host's size and the editor's own resize request, rounding of the scale to steps, or a stale size answered to Live. Record the sequence of host calls in the notes (a debug log behind an env var is fine, removed or off by default after).

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Cause: nice-plug 0.4.2 VST3 checkSizeConstraint -> OrbHandle::adjust_size -> editor::adjust_logical(proposed, current = window.size()); 'the side the host changed more decides' depends on the current size. Live proposes the cursor's size each mouse event (absolute, from the drag) and sizes its window to the answer, onSize -> set_size makes it the current size; with the cursor off the rule's diagonal the width candidate and the height candidate differ and each answer makes the other side the one that changed more: the size alternates.
2. Test first (reproduce): a VST3 fake host in tests/clap_gui.rs (macOS, harness-less, main thread): load the library, IComponent -> IEditController::createView, attached to an NSView, then replay a corner drag along a cursor path off the diagonal (checkSizeConstraint(cursor rect) then onSize(answer), getSize after); assert the widths follow the cursor monotonically and that the answer for a rect does not depend on the current size. Plus a unit test of adjust_logical on the same sequence.
3. Fix: a rule that is a function of the proposed size only (stateless, so no answer can flip the next one): the largest size of the rule that fits inside the proposed size (whole points, at least half the panel), as JUCE's VST3 wrapper does for a fixed aspect ratio; idempotent on sizes of the rule (a host's re-check of the answer gives it back). Edge drags: shrinking by one edge works, growing by one edge alone does not (the corner does).
4. Keep REAPER: clap_gui's sizes, the editor tests updated for the new rule; docs/plugin.md section 10.
5. A debug log of the host's size calls (checkSizeConstraint/adjust_size, set_size/onSize, getSize, the requests) behind ORB_PLUGIN_SIZE_LOG=FILE, off by default, for the user's Live capture; docs/building.md variable table.
6. cargo test, clippy, nightly fmt; bundles built in the worktree and validated; the user's Live and REAPER check left open (status To Do).

Cause: OrbHandle::adjust_size (nice-plug 0.4.2 wrapper/vst3/view.rs 734-772 checkSizeConstraint) -> editor::adjust_logical(proposed, current = window.size()) chose the side that changed more relative to the CURRENT size.
